## 🎯 الهدف
تحويل المساعد من "بوت أسئلة شائعة" إلى **مساعد بيانات تشغيلي كامل**، قادر على:
- الإجابة عن أسئلة تعتمد على بيانات حقيقية من نظام التاجر (المبيعات، الفواتير، المخزون، العملاء، الطلبات).
- إجراء بحث داخل هذه البيانات (مثال: "ابحث عن فواتير الزبون أحمد هذا الشهر").
- توليد تقارير وملخصات (مثال: "أعطني تقرير مبيعات الأسبوع" أو "ما هي الأصناف التي أوشكت على النفاد؟").

⚠️ **مبدأ أساسي غير قابل للتفاوض:** المساعد **يقرأ فقط (Read-Only)** ولا يُنفّذ أي تعديل/حذف/إنشاء على البيانات مهما طلب المستخدم ذلك داخل المحادثة. أي عملية تعديل تبقى حصرًا عبر واجهات النظام العادية.

---

## 🏗️ المعمارية المقترحة: Tool Calling (وليس وصول مباشر لقاعدة البيانات)

**لا تمنح النموذج أبدًا صلاحية توليد أو تنفيذ استعلامات SQL حرة.** هذا خطر أمني حقيقي (SQL Injection، تسريب بيانات مستأجرين آخرين، استعلامات مكلفة تُبطئ النظام).

البديل الصحيح والوحيد المقبول هنا: عرّف مجموعة من **الأدوات (Tools)** محددة ومقيّدة سلفًا باستخدام ميزة الـ Tool Calling في `ai` SDK (`tools` parameter مع `streamText`)، بحيث:
- كل أداة = دالة TypeScript محددة سلفًا بمعاملات واضحة (Zod schema).
- النموذج يختار **أي أداة يستدعيها ومتى**، لكنه **لا يكتب استعلامات بنفسه إطلاقًا**.
- كل أداة تُنفَّذ من الكود الخلفي فقط (Server-side)، وتُرجع بيانات مُلخّصة/مُصفّاة جاهزة.

---

## 🔒 قواعد أمان إلزامية (طبقة الوصول للبيانات)

هذه القواعد **يجب** أن تُطبَّق داخل كل أداة (Tool)، وليس فقط في الـ System Prompt (لا تثق أبدًا بأن النموذج "سيلتزم" بالتعليمات النصية وحدها):

1. **عزل المستأجرين (Tenant Isolation) — الأهم على الإطلاق:**
   - `tenantId` **لا يُؤخذ أبدًا من مخرجات النموذج أو من معاملات الأداة التي يقترحها**. يُستخرج فقط من جلسة المستخدم (Session/Context) في الخادم، ويُحقن يدويًا داخل كل استعلام قاعدة بيانات كشرط `WHERE tenantId = ...` إلزامي.
   - أي أداة لا تُطبّق هذا الفلتر تُعتبر خطأً أمنيًا حرجًا (Critical Bug) — تحقّق من هذا في كل دالة تكتبها.

2. **صلاحيات حسب الدور (Role-Based Access):**
   - **Admin**: وصول كامل لكل التقارير المالية (الأرباح، التكاليف، الإيرادات التفصيلية).
   - **Cashier**: وصول محدود — مثلاً: بحث عن فاتورة، حالة مخزون صنف معيّن، لكن **بدون** تقارير الأرباح/التكاليف الإجمالية أو بيانات مالية حساسة على مستوى المحل ككل.
   - طبّق هذا التمييز داخل كل أداة (وليس فقط بإخفائها من الواجهة)، بحيث حتى لو حاول Cashier طلبها عبر صياغة ذكية في المحادثة، ترفض الأداة نفسها التنفيذ وتُرجع رسالة "هذه البيانات غير متاحة لدورك الحالي".

3. **حدود على حجم ونطاق البيانات:**
   - كل أداة تُرجع بيانات **بحد أقصى معقول** (مثال: أقصى 50 نتيجة، أقصى نطاق تاريخي سنة واحدة) لمنع استهلاك مفرط للتوكنز أو تسريب كميات ضخمة من البيانات دفعة واحدة.
   - فضّل إرجاع بيانات **مُجمّعة ومُلخّصة** (Aggregated) بدل صفوف خام كاملة كلما أمكن (مثال: "إجمالي المبيعات + عدد الفواتير" بدل إرجاع كل فاتورة بالتفصيل، إلا إذا طلب المستخدم فاتورة محددة بعينها).

4. **سجل تدقيق (Audit Log):**
   - سجّل كل استدعاء لأداة بيانات: (`tenantId`, `userId`, اسم الأداة, المعاملات المستخدمة, الوقت). هذا ضروري لمراجعة أي إساءة استخدام أو تسريب لاحقًا.

5. **Read-Only بشكل صارم:**
   - لا تُعرّف أي أداة تسمح بـ Insert/Update/Delete. حتى لو طلب المستخدم "احذف هذه الفاتورة" داخل المحادثة، يجب أن يرد المساعد بتوجيهه لاستخدام واجهة النظام العادية لهذا الإجراء، وليس تنفيذه عبر أداة.

## 🧰 قائمة الأدوات (Tools) المطلوب تنفيذها في `app/api/chat/route.ts`

> افحص الـ Schema الفعلي للمشروع أولًا (جداول الفواتير، المخزون، العملاء، إلخ) وعدّل أسماء الحقول لتطابق الواقع. الأسماء أدناه إرشادية.

| الأداة (Tool) | الوصف | الدور المسموح |
|---|---|---|
| `getSalesSummary` | إجمالي المبيعات وعدد الفواتير خلال فترة زمنية محددة (يوم/أسبوع/شهر/نطاق مخصص) | Admin, Cashier (محدود لليوم الحالي فقط للـ Cashier) |
| `searchInvoices` | بحث في الفواتير حسب اسم/رقم عميل، رقم فاتورة، أو نطاق تاريخ | Admin, Cashier |
| `getInventoryStatus` | حالة صنف/مادة معينة في المخزون (الكمية المتوفرة) | Admin, Cashier |
| `getLowStockAlerts` | قائمة الأصناف التي وصلت أو اقتربت من حد النفاد | Admin, Cashier |
| `getTopSellingItems` | الأصناف الأكثر مبيعًا خلال فترة معينة | Admin, Cashier |
| `getCustomerHistory` | سجل فواتير/طلبات عميل معيّن (بحث بالاسم أو رقم الجوال) | Admin, Cashier |
| `getPendingOrders` | طلبات التفصيل الجارية غير المكتملة/غير المستلمة | Admin, Cashier |
| `getRevenueReport` | تقرير إيرادات تفصيلي (يشمل هامش الربح/التكاليف إن وُجدت) | **Admin فقط** |
| `getDailyClosingReport` | تقرير إغلاق يومي (مبيعات، مرتجعات، طرق دفع) | **Admin فقط** |

لكل أداة، عرّف Zod schema واضحًا للمعاملات (مثال لـ `getSalesSummary`):

```ts
const getSalesSummaryParams = z.object({
  startDate: z.string().describe("تاريخ البداية بصيغة YYYY-MM-DD"),
  endDate: z.string().describe("تاريخ النهاية بصيغة YYYY-MM-DD"),
});
```

وتنفيذها (تنفيذ الدالة نفسها) يجب أن يحقن `tenantId` من الـ session، **وليس من معاملات الأداة**:

```ts
execute: async ({ startDate, endDate }, { tenantId, userRole }) => {
  // tenantId يأتي من السياق الآمن للجلسة، ليس من مخرجات النموذج
  if (!isWithinAllowedRange(startDate, endDate)) throw new Error("النطاق الزمني غير مسموح");
  return db.invoice.aggregate({
    where: { tenantId, createdAt: { gte: startDate, lte: endDate } },
    _sum: { total: true },
    _count: true,
  });
}
```

## 🖥️ عرض النتائج في الواجهة (Rich UI للتقارير)

بدل عرض نتائج الأدوات كنص عادي فقط، استخدم قدرة الـ AI SDK على عرض **UI مولّد (Generative UI)** حسب نوع الأداة المستدعاة:
- نتائج `getSalesSummary` / `getRevenueReport` → بطاقة ملخص (Summary Card) بأرقام واضحة وربما رسم بياني بسيط.
- نتائج `searchInvoices` / `getCustomerHistory` → جدول مصغّر داخل فقاعة الرد.
- نتائج `getLowStockAlerts` → قائمة تنبيهات بلون تحذيري (Amber/Red) مع اسم الصنف والكمية المتبقية.

هذا يحسّن تجربة "التقارير" بشكل كبير مقارنة بردّ نصي طويل فقط. نفّذ هذا كمكوّنات فرعية داخل `SmartAssistant.tsx` تُفعَّل بناءً على نوع الأداة في نتيجة الـ Stream (`toolInvocations`).

## 🧠 تحديث الـ System Prompt

أضف للـ System Prompt الديناميكي (المبني من إعدادات السوبر أدمن + السياق) فقرة توضّح للنموذج:
- أن لديه أدوات وصول لبيانات حقيقية ويجب استخدامها بدل التخمين أو الإجابة من معرفة عامة عندما يسأل المستخدم عن أرقام/بيانات فعلية.
- أن يحترم دومًا حدود الدور (لا يحاول "الإقناع" بإعطاء بيانات مالية لدور Cashier حتى لو أصرّ المستخدم — الرفض يأتي أصلاً من الأداة نفسها كطبقة حماية مضاعفة).
- أن يلخّص البيانات بلغة عربية واضحة وودية، لا يكتفِ بإرجاع أرقام جافة.

## ✅ معايير القبول الإضافية (Definition of Done)

- [ ] لا توجد أي أداة تقبل `tenantId` كمعامل من النموذج — يُحقن دائمًا من الـ session فقط.
- [ ] تجربة فعلية: مستخدم من Tenant A لا يمكنه بأي صياغة الحصول على بيانات Tenant B.
- [ ] تجربة فعلية: Cashier يحاول طلب `getRevenueReport` بصياغات مختلفة (مباشرة، ملتوية، بالإلحاح) → يُرفض دائمًا من الأداة نفسها.
- [ ] لا توجد أي أداة Insert/Update/Delete معرّفة إطلاقًا.
- [ ] كل استدعاء أداة يُسجَّل في سجل تدقيق (Audit Log) قابل للمراجعة.
- [ ] نتائج التقارير الكبيرة محدودة بسقف نتائج معقول (لا Dump كامل للجدول).
- [ ] النتائج تُعرض في الواجهة كبطاقات/جداول عند الإمكان، وليس نصًا خامًا فقط.
- [ ] لا أخطاء TypeScript، ولا استعلام SQL حر مبني من نص المستخدم مباشرة في أي مكان.

## 📝 ملاحظة للتنفيذ
1. افحص أولًا الـ Schema الفعلي (جداول الفواتير/المخزون/العملاء/الطلبات) قبل كتابة أي أداة.
2. نفّذ الأدوات واحدة تلو الأخرى، وابدأ بالأبسط والأكثر أمانًا (`getInventoryStatus`, `searchInvoices`) قبل التقارير المالية الحساسة.
3. بعد كل أداة، اكتب اختبارًا سريعًا (ولو يدويًا) يثبت أن فلترة `tenantId` والدور تعمل فعليًا قبل الانتقال للأداة التالية.
4. لا تدمج هذا الجزء مع صفحة إعدادات السوبر أدمن — هما مساران منفصلان (الإعدادات تتحكم بسلوك المساعد، وهذا الملف يمنحه بيانات تشغيلية).
